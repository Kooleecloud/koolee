## 1. What Koolee is

Doorstep luggage pickup delivered to the airline's bag drop. NYC (JFK / LGA /
EWR). Turborepo monorepo: three Next.js apps (`web` customer, `agent` PWA,
`admin` ops) over `packages/core` (all domain logic) and `packages/db`
(Drizzle + Postgres/Supabase). Architecture, copy rules, env matrix:
[README.md](README.md).

### 3.1 Migration state — verified, not assumed (2026-08-10)

Earlier revisions of this file claimed hosted "still owes 0012/0013/0014" and
that `0013` was "generated, NOT applied to any database". **Both were wrong.**
Established by matching every row in `drizzle.__drizzle_migrations` against this
checkout by sha256 content hash, on both databases:

- **Local and hosted each carry all 16 migrations `0000`…`0015`.** Their
  structures are identical: 22 tables, 192 columns, 71 indexes, 63 constraints,
  74 defaults, 3 triggers, 2 RLS policies — no differences.
- **Hosted has a 17th, ORPHAN journal row** (`hash 5eaa1bc62687…`,
  `created_at 1785717701364`), sitting between `0002` and the current `0003`. It
  is the old `otp_send_log` 0003: applied and recorded, then regenerated and its
  file deleted, so the row survives with no file. **Leave it alone.** Drizzle's
  migrator reads only the newest row (`order by created_at desc limit 1`) and
  compares that timestamp to each file's `folderMillis`, so an extra row in the
  middle is invisible to it. Deleting it would be a write to production
  migration history for zero functional gain.
- **`pnpm db:status` used to get this exactly backwards**, reporting "Applied:
  17 of 16 … 1 migration AHEAD … Pull before migrating anything." It compared
  row COUNTS. It now compares hashes, names missing tags, reports orphans as
  orphans, and adds the check that matters most: a pending migration whose
  timestamp is **at or below** the database's watermark is **STRANDED** —
  `db:migrate` will skip it forever with no error. That is how the 0003 rework
  went wrong; regenerate such a migration, never edit journal rows.

**The one real divergence found** was RLS, and it ran the wrong way: hosted had
an out-of-band `ensure_rls` event trigger (`public.rls_auto_enable()`, in no
migration in this repo) switching RLS on for all 22 public tables, while local
had it off on 20 of them — so **local was the less safe environment**, and a
client-side read that hosted refuses would pass every local test. Migration
`0016_uniform_rls_baseline` encodes hosted's stance for every environment. It
changes no application behaviour: the app connects as `postgres`, which carries
`rolbypassrls` (`rolsuper=false`), and no table uses FORCE RLS. Note `anon` /
`authenticated` / `service_role` each hold 154 table-privilege grants, so on
those 20 policy-less tables the deny is RLS, not privilege — worth revisiting
separately.

## 7. Standing constraints (do not relearn these)

- Copy rules: "delivered to your airline's bag drop" — never overclaim, no
  fabricated numbers ([README](README.md)).
- **Documentation lives under `docs/`, never in the repo root.** The only two
  root markdown files are `README.md` (the entry point GitHub renders) and this
  tracker. Build logs go in `docs/run-reports/`, repo-wide guides in `docs/`,
  feature walkthroughs in `docs/features/`, and anything app- or
  package-specific next to the code it describes.
- `custody_events` is append-only (trigger + no update/delete helpers);
  corrections are compensating events.
- Authorization in `packages/core`, not RLS; RLS exists only for Realtime on
  `bookings`/`custody_events`.
- Two DB connections: pooled 6543 for runtime (`prepare: false`), direct 5432
  for migrations. Never mix.
- Unknown airline cutoff ⇒ refuse to sell.
- All auth secrets (Twilio Verify, Turnstile secret) live in the Supabase
  dashboard only; the app forwards `captchaToken` and never calls siteverify.
- Upgrade sends go through ONE guard (`guardUpgradeOtpSend`): throttle +
  reconciliation in a single transaction, user lock before destination lock.
  Never split them back into separate transactions.
- `packages/core` takes credentials as VALUES, injected via `createRuntime()` —
  payments, notifications, extraction and the event emitter are all seams.
  Exactly one exception, and it is not a bug to "fix" casually:
  `auth/hash-destination.ts` reads `OTP_LOG_HMAC_KEY` and throws when unset.
- `booking/exception_raised` is emitted by CORE, from `applyTransition` and
  the webhook handler's `moveBooking` — the two choke points a booking row can
  reach `exception` through. Never re-add an emit at a call site or in an app
  route; that is how six of seven paths went silent for a whole slice. Emission
  never throws: the transition already committed.
- `bookings.ref` (`KOO-XXXXX`) is DISPLAY AND SUPPORT ONLY. Never authenticate,
  authorize or look a booking up by it on a public route — 32^5 is fine for
  uniqueness and hopeless as a secret. Trip URLs stay UUID-addressed.
- Never revert a migration-journal entry on an assumption about DB state —
  verify against the DB or write a corrective migration.
- Migration state is established by CONTENT HASH, never by row count, and never
  from this file's prose (which has been wrong twice). `pnpm db:status` is the
  tool; it is read-only and safe against production. Hosted carries one orphan
  journal row on purpose — do not "clean it up". A pending migration whose
  timestamp is at or below the target's watermark is silently skipped forever:
  regenerate it, never edit journal rows. See §3.1.
- **Check `packages/ui` before building any input, control or layout piece,
  and lift a component there the moment a second app needs it.** Two apps
  quietly growing their own date picker is how the consoles drift apart, and
  the drift is invisible until a customer and an operator read the same field
  differently. Worked examples: `DateTimeField` (built for the funnel's flight
  step, now also the admin agreements effective-date field — it posts a
  wall-clock string, so it is a drop-in for `<input type="datetime-local">`)
  and `downscalePhoto` (`@koolee/ui/lib/photo`, shared by the agent's bag
  capture and the customer's passport upload — the 1 MB Server Action 413 it
  prevents is identical in both). Non-React helpers go in `packages/ui/src/lib`
  behind a package subpath, NOT in the component barrel.
- The agreement editor's extension list, `packages/ui/src/lib/agreement-markdown.ts`
  and `<Markdown>` are ONE contract, not three files to keep in step. The AST in
  that module is the definition of what an agreement can contain; the editor and
  the customer-facing renderer are both consumers of it. Widening the editor
  without widening the AST means an operator formats a clause and the customer
  silently never sees it — on a document they are being asked to agree to. Add
  to the AST first; the round-trip tests fail until you do.
- An agreement version FREEZES the moment it takes effect (migration 0024, plus
  the guard in `updateScheduledAgreementVersion`). A version scheduled for the
  future is editable precisely because it cannot have been accepted — which is
  why the product has no separate draft state. Never add an edit path for a
  version already in force: `agreement_acceptances` references it by id, so
  editing it rewrites what past acceptors agreed to.
- The verification visit's identity gate has NO override. Both halves —
  a current-version agreement acceptance and an `agent_confirmed` passport —
  are enforced in `packages/core` (`recordBagSealed`, `completeVerificationVisit`),
  not in the agent UI, because a server action stays a reachable POST whatever
  the UI renders. A blocked agent files an exception; never add a bypass.
- `passport_verifications` must never gain a column describing the document
  (number, name, DOB, nationality, MRZ, expiry). The table has to be worthless
  to anyone who can read it. A validity checker returns a STATUS, never fields.
- Agreement "current" is `max(version)` where `effective_from <= now()`. Never
  add an `is_active` boolean.
- **Agreement versions PIN per booking.** The version a booking accepts governs
  it for life; publishing a newer one never re-asks a booking that has already
  accepted, and `UNIQUE (booking_id)` on `agreement_acceptances` (0025) makes a
  second acceptance impossible. Never reintroduce a "has this booking accepted
  the CURRENT version" gate — that model blocked pickups over a wording change
  while leaving in-transit bookings alone (not a principle, an artifact of gate
  placement), and re-asking at a doorstep with the bags packed is consent under
  duress, which is not consent worth having. A publish still may not be
  retroactive: it decides which version NEW bookings pin to, and backdating
  rewrites which terms a booking sold an hour ago was sold under.
- A storage policy that needs the staff roster calls
  `public.is_active_staff(auth.uid())` (0009), never an inline
  `EXISTS (… staff_members …)` — the subquery runs as `authenticated`, which
  has no privilege on that table. This has now been got wrong twice (0008, 0022).
- Every human-facing time renders in the BOOKING's zone (`bookings.display_tz`,
  the departure airport's) — never the viewer's, never the server's, and always
  with the zone abbreviation. `booked_from_tz` is metadata and must never reach
  a formatter. Full rules: [docs/TIME.md](docs/TIME.md).
